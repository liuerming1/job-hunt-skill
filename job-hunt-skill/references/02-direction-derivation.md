# 02 — 方向推导（direction derivation）

> Step 1。本 skill 与原仓库（MadsLorentzen/ai-job-search）的根本差异：搜索方向由 AI 从简历反推，而不是让用户手写查询模板。方向是「可执行的搜索词」，不是抽象的职能描述。

## 产出规格

从 profile 反推 **3 个**岗位方向。每个方向一张卡：

| 字段 | 要求 | 反例 |
|---|---|---|
| 方向名 | 一个可直接放进 BOSS 搜索框的词 | 「商业化方向」✗ / 「商业化产品经理」✓ |
| 匹配理由 | 指向简历里的哪几条证据（引用 profile 原句） | 「比较匹配」✗ / 「简历 P3 项目主导过广告投放系统」✓ |
| 搜索关键词 | 2-3 个 BOSS 可用变体（同职能不同叫法） | 「产品经理、B端产品经理、商业化产品经理」 |
| 预期匹配度 | 高 / 中 / 保底 | — |
| 风险 | 这个方向下简历最弱的一环 | 「缺支付行业背景，面支付岗会被追问」 |

## 推导方法

按三条线索交叉：

1. **履历主轴**：最近一份工作的职能 + 行业，推导「顺着走」的方向（预期：高）
2. **技能迁移**：硬技能里可跨行业复用的部分，推导「 sideways」方向（预期：中）
3. **职业目标对齐**：config.json 里的职业目标三条，推导「想去的」方向（预期：保底，风险写实）

三个方向应该覆盖这三种性质，避免三个方向全挤在主轴上。

## 「同一个方向」的判定标准

用户给了目标方向时，和 AI 推的方向比对：**关键词重合 + 职级一致**。

- 用户说「AI 产品经理」，AI 推的里有「AI 产品经理」→ 算重合，不补搜
- 用户说「AI 产品经理」，AI 推的是「B 端产品经理」→ 不算，补搜

判定宁可宽松，不要错杀：补搜的成本是几条请求，漏搜的成本是用户看不到他真正想要的岗位。

## 分支逻辑

```
用户给了方向？
├── 没给 ──→ 只搜 AI 推的 3 个
└── 给了 ──→ AI 的 3 个里有语义重合的吗？
            ├── 有 ──→ 3 个（不重复搜）
            └── 没有 ──→ 3 + 1 = 4 个（用户方向 + AI 的 3 个）
```

## 展示与继续

方向卡片在对话里展示给用户看一眼，**不等确认就往下走**（Step 1·5 问城市）。用户插话调整时即时采纳：替换掉的方向不再抓取，新方向按 10 条上限抓。

方向推导错误的信号（抓取后回查用）：某个方向 10 条里 8 条以上被硬门 FAIL 或匹配分 <30 → 方向错了，该回去改方向或换关键词变体，**而不是抓更多**。
