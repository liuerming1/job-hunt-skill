# 03 — 职位评估（三道硬门 + 五维打分）

> Step 3 与单点评估入口共用。结构改造自原仓库 `04-job-evaluation.md`：逻辑不变、门槛全换成中国场景。

## 流程：先硬门，后打分

硬门跑在打分之前，FAIL 直接出局，不进打分环节。但 **FAIL 的必须可见可复查**：折叠成「已过滤 N 条」，每条附 FAIL 门 + JD 原文引用。AI 判错学历要求时用户要能捞回来——不能静默丢弃。

## 三道硬门

| 门 | 判定 | 说明 |
|---|---|---|
| 学历门 | JD 要求高于简历实际学历 → FAIL | 专升本、非全日制需单独标注：JD 写「统招/全日制本科」而简历是非全日制 → FAIL；JD 只写「本科」→ PASS 并注明 |
| 履历门 | JD 明确排除外包/派遣背景，或要求特定行业年限而简历不符 → FAIL | 外包经历本身不 FAIL，只标记；JD 明确排除才 FAIL |
| 工时门 | JD 写明 996 / 大小周 / 单休，与 config.json「工时底线」冲突 → FLAG 或 FAIL | 用户 config 里写了「不能接受 996」→ FAIL；没写 → FLAG 交用户判断。**工时底线是三个细分字段（2026-10-28 修订）：每周休几天底线 / 休息日是否必须周末 / 周末排课是否可接受，判定时逐字段对**。例：教培岗 JD 写「周一周二双休」＝休两天但周末上课——只撞「必须周末双休」或「不接受周末排课」才 FAIL，用户接受周内休两天则 PASS |

**FLAG 规则**：FLAG 的必须引用 JD 原文，交用户判断，不静默处理。这是原仓库规则，照搬。

**城市匹配不是硬门，是五维里的 Pass/Fail 维度**（见下）：JD 工作地与目标城市（Step 1·5 确认）不一致 → 直接 Fail；远程/混合办公岗位单独分档标注，不与现场岗混排。

## 五维打分

| 维度 | 权重 | 中国场景适配 |
|---|---|---|
| 技能匹配 | 30% | 关键词表识别中英文混写（「用户增长」=「UG」） |
| 经验匹配 | 25% | 按职能实质比，不按 title 比（「产品经理」vs「解决方案经理」可能同质） |
| 文化匹配 | 15% | 加入「大厂螺丝钉 vs 创业公司全栈」「汇报层级深度」 |
| 城市匹配 | Pass/Fail | JD 工作地 = 目标城市 → Pass；不一致 → Fail；远程/混合单独分档 |
| 职业契合 | 30% | config.json 的职业目标三条 + 能量/消耗任务清单 |

加权总分 = (技能×30 + 经验×25 + 文化×15 + 职业契合×30) / 100。城市匹配 Fail 的不参与排序（直接沉底并标注）。

## 评估每维度的方法

- **技能匹配**：JD 任职要求逐条 vs profile 硬技能。命中给分、部分命中半分、缺失扣分。缺失的列进「差距清单」
- **经验匹配**：职能实质 + 年限 + 行业三层比。title 不同但职责同质的写明理由
- **文化匹配**：公司规模/融资阶段 vs 简历所在公司量级；汇报层级从 profile 职级线索推
- **职业契合**：JD 的日常工作内容 vs 职业目标三条 + 能量/消耗清单。这是主观性最强的一维，写结论时必须引用 config 原文

## 阈值（沿用原仓库）

| 分数 | 结论 |
|---|---|
| 75+ | 强烈推荐 |
| 60-74 | 推荐 |
| 45-59 | 慎重 |
| 30-44 | 大概率跳过 |
| <30 | 放弃 |

## 产出格式（`postings/.../eval.md`）

```markdown
# 评估：<公司> · <职位>
总分：72（推荐）  城市匹配：Pass
## 硬门：学历 PASS / 履历 PASS / 工时 FLAG（JD 原文：「能承受高强度工作节奏」→ 交用户判断）
## 五维：技能 24/30 · 经验 19/25 · 文化 10/15 · 职业契合 19/30
## 一句话理由：……
## 差距清单：……
```

一句话理由会直接进 Step 3·5 的候选列表，必须能让用户不点开详情就理解为什么这个分。
